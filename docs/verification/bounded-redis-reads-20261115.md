# Bounded Redis reads: current port of part of #19

Compared old #19 head fa9b801174d83dae9558edccd361c9d864b5b3e4 and current
Stable-02-01 89834175e9cdf6c4de9c7bc254c0e7782ac1ea5f. The old credential
reader had a six-second subprocess deadline and rejected failed/error replies;
the current reader had neither. A stalled local Redis CLI could indefinitely
stall credential loading; a failed response could become an API credential.
The already time-bounded settings read also parsed nonzero-exit output as
configuration and persisted it.

This narrow port bounds HGET to six seconds and preserves HGETALL's existing
three-second deadline and one-minute settings cache. Both reject subprocess
failure and Redis error replies. Missing binaries and timeouts yield no data;
there is no retry, credential logging, cross-connection fallback or new write.
Successful scalar/hash values, including zero, false, JSON and empty strings,
retain their previous interpretation. Failed settings reads do not overwrite
the persisted settings file. This does not redesign Redis namespaces, shared
Pulse storage, service units or retained policies; #19 remains open.

Five targeted offline tests fail on the pre-fix source (11 failed subcases,
two timeout/missing-binary exceptions) and pass after the port. They use mocked
subprocess responses, so assert the deadline arguments rather than claiming a
wall-clock outage/venue acceptance. The required workflow explicitly runs them.
The restore patch and both engine blob pins are regenerated by
scripts/update_restore_pin.py. Whitespace-only context lines inside the unified
restore patch are required patch syntax, not trailing whitespace in Python.
Full test/build/typecheck and exact-head CI outcomes are retained in the overall
verification report. No live account, service, Redis server or deployment was
changed; no new financial sample or execution PF is claimed.
